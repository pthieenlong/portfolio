I've rebuilt my portfolio more times than I'd like to admit. Next.js, then Gatsby, a brief SvelteKit experiment, and now Astro. This time it feels right — here's why.

## The Problem with Using a Full SPA Framework for a Portfolio

My Next.js portfolio shipped ~200KB of JavaScript for a site that's mostly static content. The interactivity was minimal: a theme toggle, some scroll animations, and a contact form. That's it.

Next.js is incredible for dynamic apps. But for a portfolio? It's overkill.

## What Makes Astro Different

Astro's core idea is **Islands Architecture**: render everything as static HTML by default, and hydrate only the components that actually need JavaScript.

```
Traditional SPA:     [ Full JS bundle → hydrate everything ]
Astro:               [ Static HTML + tiny islands of JS where needed ]
```

This means:

```astro
---
// This runs at build time only — zero JS shipped
const posts = await getCollection('blog');
---

<ul>
  {posts.map(post => (
    <li>
      <a href={`/blog/${post.slug}`}>{post.data.title}</a>
    </li>
  ))}
</ul>
```

## The `client:*` Directive System

The most powerful concept in Astro: you control exactly when and how components hydrate.

```astro
<!-- Load JS immediately (above the fold) -->
<Header client:load />

<!-- Load JS when component is visible -->
<AnimatedSection client:visible />

<!-- Load JS when browser is idle -->
<Analytics client:idle />

<!-- Never hydrate — server render only -->
<Footer />
```

This is why Astro sites consistently score 95-100 on Lighthouse Performance without any extra effort.

## Content Collections Are Excellent

Astro's content collections with Zod schemas give you type-safe content:

```typescript
// src/content/config.ts
const blog = defineCollection({
  schema: z.object({
    title: z.string(),
    publishedAt: z.coerce.date(),
    tags: z.array(z.string()),
    draft: z.boolean().default(false),
  }),
});
```

Now your frontmatter is validated at build time. Missing a required field? Build fails with a clear error. This alone has saved me from countless "why is this undefined" bugs.

## What I Miss from Next.js

Honestly? Not much for this use case. But:

- **API Routes** are more limited (though Astro's endpoints work fine for simple cases)
- **Server-side rendering** story is there but Next.js has a larger ecosystem
- **Incremental Static Regeneration** is Next.js-specific

## My Current Astro Stack

```
Framework:  Astro 5.x
UI:         React (for interactive components only)
Styling:    TailwindCSS 4.x
Animation:  Framer Motion
Content:    MDX + Content Collections
Deploy:     Vercel
```

## The Verdict

For portfolios, blogs, documentation sites, and marketing pages — Astro is the right tool. It ships less JavaScript by default than any other framework I've used, while still letting you reach for React, Vue, or Svelte when you actually need interactivity.

My Lighthouse scores went from 72-80 (Next.js) to consistently 98-100 after the Astro rebuild. For a content site, that's not a marginal improvement — it's a fundamentally better architecture.
